▶ データ信頼性・欠損時ルール

「その数字は新しいか・信じてよいか・無いときどうするか」。業務OSとして判断・監査に耐えるための取り扱い基準。原則：欠損を勝手に0にしない（NULLは「—」表示）／古い値は鮮度を必ず表示する。
データ系統 更新頻度 信頼度 欠損・古い時の扱い 意思決定への影響
① SCADA リアルタイム〜30分 高（機器直結） 直近値を保持し「○分前」と鮮度表示。通信途絶は「データなし」明示し現地確認へ。0埋め禁止 発電量・アラームが見えない＝停止判断の根拠が消える。最優先で復旧/現地確認
② 気象API 1時間毎 中（予報は外れる） 前回キャッシュを表示＋鮮度。気象庁の注意報・警報を予報より優先 高所作業可否・出力予測がぶれる。安全側（作業中止寄り）に倒す
③ JEPX 日次（前日確定） 高（公式値） 未取得は前日価格で代用し「暫定」表示 売電額予測のみに影響。運用・安全判断には波及しない
④ 点検・作業管理 都度／CSV取込 中（人手入力） 未入力は「対象外」と区別し「未実施」として警告。期限超過はハイライト 点検漏れ・期限超過を見逃す＝保安義務に直結。未入力ゼロを担保
⑤ 計算（導出） 日次バッチ 06:00 元データ依存 元データ欠損なら計算結果もNULL→「—」表示（0や前日値で埋めない） KPI・稼働率が歪む。欠損由来かを必ず区別して読む
⑥ 手入力（朝会） 朝会中 人依存（主観） 空欄可。ただし判断・承認は「理由＋承認者＋時刻」を証跡として残す 証跡が無いと後から検証不能。重要判断ほど記録を必須化
⚖️ 欠損・低信頼データに基づく最終判断は電気主任技術者が行う。 画面はデータの鮮度（○分前）・信頼度・暫定/未実施の別を必ず示し、利用者が「この数字をどこまで信じるか」を判断できるようにする。データに基づく業務操作・承認は各ライブ画面で行い、本書はあくまで出所と取り扱いの地図。

▶ SCADAだけでは賄えない部分（重要）

SCADAが担うのは全体の約 4割（昨日タブのほぼ全て）。
本日タブ は SCADA（現在値）＋ 気象API（残時間予測）＋ JEPX ＋ 点検計画 の4系統が必要。
明日タブ は SCADA の出番はほぼなく、気象API・JEPX予測・点検計画が主役になる。

最小構成の推奨: daily_kpi.csv（3行）/ wtg_status.csv（138行）/ time_series.csv / inspection_plan.csv / alarm_list.csv の5ファイル。
気象APIとJEPXは Python 10行で自動取得可能。点検計画は既存のExcelをCSV保存するだけで接続できる。

今回の追加マッピングで判明した追加データ要件：
① staff_roster.csv（要員名簿・保有資格）— 工数・資格チェックに必要。Excelで管理中なら同様にCSV化で対応可。

④ forecast_accuracy_logs.csv（計画値誤差履歴）— インバランス影響額の計算に使用。SCADAまたはアグリゲーターから取得。

▶ daily_kpi テーブルの作り方（詳細計算フロー）

毎朝 06:00 に Python ETL が実行され、1日あたり 3行（昨日実績・本日見込み・明日予測）を計算して UPSERT します。
この3行が KPI比較表・アグリゲーター連絡・インバランス影響額のすべての数値の源泉です。

① type = 'actual'　　昨日実績

前日の scada_30min 全48コマを集計。
SCADAが記録した発電量・風速の実測値から計算。
議事録の「前日決定の結果」・KPI比較表「昨日実績」列に表示。

② type = 'today'　　本日見込み

確定分（朝までの scada_30min）＋
残時間推計（weather_cache × パワー曲線）
を足し合わせて1日分を推計。KPI比較表「本日見込み」列に表示。

③ type = 'tomorrow'　明日予測

全48コマを weather_cache（翌日72時間予報）× パワー曲線で推計。
SCADAデータは使わない（まだ存在しない）。
KPI比較表「明日予測」列に表示。

計算フロー（Python ETL が毎朝06:00に実行）

# ─── STEP 1: 昨日実績（type='actual'）を計算 ─────────────────────
yesterday = today - 1日

power_mwh = SUM(scada_30min.power_output_mwh) WHERE date = yesterday
availability_pct = (46×48 - 停止コマ数) / (46×48) × 100
revenue_man_yen = power_mwh × 18円/kWh × 1000 ÷ 10000 # MWh→万円
avg_wind_ms = AVG(scada_30min.wind_speed_ms) WHERE date = yesterday
jepx_avg = AVG(jepx_spot_prices.area_price_tokyo) WHERE delivery_date = yesterday
forecast_error_pct= forecast_accuracy_logs.error_pct WHERE date = yesterday

# ─── STEP 2: 本日見込み（type='today'）を計算 ──────────────────────
now_slot = 現在時刻の30分コマ番号 # 例: 7:00なら slot=14

power_actual_so_far = SUM(scada_30min) WHERE date=today AND slot <= now_slot
power_forecast_rest = SUM(
    weather_cache.wind_speed_ms → power_curve → kW → MWh変換
) WHERE datetime_hour > now AND date=today
power_mwh = power_actual_so_far + power_forecast_rest
# revenue / availability / wind_avg → 同様に計算

# ─── STEP 3: 明日予測（type='tomorrow'）を計算 ─────────────────────
power_mwh = SUM(
    weather_cache.wind_speed_ms → power_curve → kW → MWh変換
) WHERE date = tomorrow # 全48コマを気象予測から推計
jepx_avg = jepx_spot_prices.area_price_tokyo WHERE delivery_date = tomorrow # JEPXが翌日分を公開済みなら使用

# ─── STEP 4: Supabaseにupsert（同じdateとtypeがあれば上書き） ──────
UPSERT daily_kpi (date, type, power_mwh, availability_pct, revenue_man_yen, avg_wind_ms, jepx_avg, forecast_error_pct)
ON CONFLICT (date, type) DO UPDATE SET ... # 毎朝最新値で上書き

曲 パワー曲線による発電量推計の方法

気象API から取得した 風速(m/s) を、GEのパワー曲線テーブル（power_curve）に当てはめて出力(kW)を求めます。

例: 風速 7.2 m/s → パワー曲線から 2,450 kW を補間
→ 30分コマなので 2,450 kW × 0.5h ÷ 1000 = 1.225 MWh
→ これを48コマ分合計すると1日の予測発電量になる

※ 46基すべてに同じ風速を使うのが最小構成。精度を上げるには WTG 位置ごとに別の座標で気象APIを呼ぶ。

注 よくある落とし穴・注意点

  • 売電額の単位変換: MWh × 18円/kWh の計算は「MWh→kWh変換 (×1000)→万円換算 (÷10000)」なので結果は × 1.8 をかけるだけ
  • UPSERT の ON CONFLICT: (date, type) に UNIQUE 制約が必要。Supabase で作成後に Index を追加する
  • type='today' の実行タイミング: 朝会は 08:00 スタートなので、06:00 に計算すると約2時間分のSCADAデータが確定済みになる。残り22時間は気象APIで補完
  • JEPX 明日分の公開タイミング: 前日 17:00 頃に公開される。ETL を 17:30 にもう1回実行して tomorrow の jepx_avg を更新することを推奨

▶ Supabase の中だけで自動化できること（外部サーバー不要）

「Python を動かすサーバーを別に用意しないといけないの？」→ ほぼ不要です。
Supabase には Edge Functions（クラウド上で動くプログラム）と pg_cron（タイマー機能）が内蔵されており、
気象API取得・JEPX取得・KPI計算のすべてを Supabase の中だけで定期自動実行できます。

✅ Supabase 内だけで完結する処理

    → Edge Function が毎時自動で呼ぶ
  • JEPX価格取得
    → Edge Function が毎日自動でダウンロード

    → Edge Function が Cockpit から呼ばれる
  • CSV アップロード処理（点検計画）
    → Edge Function がStorage→DBに変換

【実装①】気象API自動取得 — Edge Function のコード

// supabase/functions/fetch-weather/index.ts
import { serve } from "https://deno.land/std@0.168.0/http/server.ts"
import { createClient } from "https://esm.sh/@supabase/supabase-js@2"

serve(async () => {
  // Supabase クライアント（自分のDBに書き込む）
  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!
  )

  // ① Open-Meteo API を呼ぶ（阿武隈の緯度・経度を入れる）
  const LAT = 37.45 // ← 実際の緯度に変更
  const LON = 140.85 // ← 実際の経度に変更
  const res = await fetch(
    `https://api.open-meteo.com/v1/forecast?latitude=${LAT}&longitude=${LON}` +
    `&hourly=wind_speed_10m,wind_direction_10m,weathercode&forecast_days=3`
  )
  const data = await res.json()

  // ② 取得した72時間分を weather_cache テーブルにupsert
  const rows = data.hourly.time.map((t: string, i: number) => ({
    datetime: t,
    wind_speed_ms: data.hourly.wind_speed_10m[i],
    wind_dir: data.hourly.wind_direction_10m[i], // 度数（int2）
    weather_code: data.hourly.weathercode[i],
    fetched_at: new Date().toISOString()
  }))

  await supabase
    .from('weather_cache')
    .upsert(rows, { onConflict: 'datetime' }) // datetimeが同じ行は上書き

  return new Response(JSON.stringify({ ok: true, count: rows.length }))
})
💡 注意: weather_cache テーブルの datetime カラムに UNIQUE制約 を追加しておくこと（Supabase → Database → Indexes → + New Index → Unique にチェック）

// supabase/functions/fetch-jepx/index.ts
import { serve } from "https://deno.land/std@0.168.0/http/server.ts"
import { createClient } from "https://esm.sh/@supabase/supabase-js@2"

serve(async () => {
  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!, Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!
  )

  // ① JEPX の東北エリア CSVをダウンロード（翌日分）
  const tomorrow = new Date()
  tomorrow.setDate(tomorrow.getDate() + 1)
  const dateStr = tomorrow.toISOString().slice(0,10).replace(/-/g, '') // 例: "20260526"

  // JEPXの公開URL（東北エリア）※URLは変わる場合があるため要確認
  const url = `https://www.jepx.jp/electricpower/csv/spot_${dateStr}.csv`
  const res = await fetch(url)
  const csv = await res.text()

  // ② CSVをパースして jepx_spot_prices に upsert
  const lines = csv.split('\n').slice(1) // ヘッダー行を除く
  const rows = lines.filter(l => l.trim()).map(line => {
    const cols = line.split(',')
    return {
      delivery_date: dateStr.replace(/(\d{4})(\d{2})(\d{2})/, '$1-$2-$3'),
      slot_code: parseInt(cols[0]), // コマ番号(1-48)
      system_price: parseFloat(cols[5]), // システムプライス列 ※列番号は要確認
      area_price_tokyo: parseFloat(cols[6]), // エリア価格列 ※列番号は要確認
      fetched_at: new Date().toISOString()
    }
  })

  await supabase.from('jepx_spot_prices').upsert(rows, { onConflict: 'delivery_date,slot_code' })
  return new Response(JSON.stringify({ ok: true, rows: rows.length }))
})
💡 注意: jepx_spot_prices テーブルの (delivery_date, slot_code) に UNIQUE制約を追加。JEPX のCSV URL・列番号は実際のファイルを見て確認すること。

【実装③】daily_kpi 計算 — PostgreSQL 関数（外部プログラム不要）

-- ① daily_kpi を計算する SQL 関数を作成
CREATE OR REPLACE FUNCTION calculate_daily_kpi(target_date DATE)
RETURNS void AS $$
DECLARE
  v_power FLOAT;
  v_wind FLOAT;
  v_avail FLOAT;
  v_jepx FLOAT;
  v_err FLOAT;
  v_stop_cnt INT;
BEGIN
  -- 発電量（昨日の scada_30min を全コマ合計）
  SELECT COALESCE(SUM(power_output_mwh), 0)
  INTO v_power
  FROM scada_30min WHERE DATE(timestamp_start) = target_date;

  -- 平均風速
  SELECT COALESCE(AVG(wind_speed_ms), 0)
  INTO v_wind
  FROM scada_30min WHERE DATE(timestamp_start) = target_date;

  -- 稼働率（停止コマを数えて逆算）
  SELECT COUNT(*) INTO v_stop_cnt
  FROM scada_30min
  WHERE DATE(timestamp_start) = target_date AND availability = false;
  v_avail := (46.0 * 48 - v_stop_cnt) / (46.0 * 48) * 100;

  -- JEPX 平均価格
  SELECT COALESCE(AVG(area_price_tokyo), 0)
  INTO v_jepx
  FROM jepx_spot_prices WHERE delivery_date = target_date;

  -- 計画値誤差
  SELECT COALESCE(error_pct, 0)
  INTO v_err
  FROM forecast_accuracy_logs WHERE date = target_date
  LIMIT 1;

  -- daily_kpi に upsert（同じ date + type があれば上書き）
  INSERT INTO daily_kpi
    (date, type, power_mwh, availability_pct, revenue_man_yen, avg_wind_ms, jepx_avg, forecast_error_pct)
  VALUES
    (target_date, 'actual', v_power, v_avail, v_power * 1.8, v_wind, v_jepx, v_err)
  ON CONFLICT (date, type) DO UPDATE SET
    power_mwh = EXCLUDED.power_mwh,
    availability_pct = EXCLUDED.availability_pct,
    revenue_man_yen = EXCLUDED.revenue_man_yen,
    avg_wind_ms = EXCLUDED.avg_wind_ms,
    jepx_avg = EXCLUDED.jepx_avg,
    forecast_error_pct = EXCLUDED.forecast_error_pct;
END;
$$ LANGUAGE plpgsql;

-- ② 手動テスト（昨日分を今すぐ計算したい場合）
SELECT calculate_daily_kpi((CURRENT_DATE - INTERVAL '1 day')::DATE);
💡 注意: daily_kpi テーブルの (date, type) に UNIQUE制約が必要。SQL Editor で
ALTER TABLE daily_kpi ADD CONSTRAINT daily_kpi_date_type_key UNIQUE (date, type); を実行しておくこと。

日本時間（JST）は UTC+9 なので、「JST 06:00 に実行したい」場合は '0 21 * * *'（前日のUTC21:00）と書きます。

JST 06:00→'0 21 * * *'（前日UTC）
JST 毎時00分→'0 * * * *'（そのまま）
JST 17:30→'30 8 * * *'（UTC 08:30）
