担当者 🔐 結果の承認ゲート
🔍 点検実施（必要時 PTW / KY / LOTO → チェックリスト入力）
承認済み計画をもとに現場へ。
安全確認は作業内容に応じて選択：
• KY（危険予知）：全点検作業で実施推奨。チームで危険箇所・対策を共有
• LOTO（施錠・タグアウト）：エネルギー機器（電気・油圧など）に触れる場合のみ必須
• PTW（作業許可証）：高所・電気工事・火気・吊上げなど特定リスク作業のみ必須
※目視巡視や計測だけの点検はLOTO不要。計画票の「安全要件」で個別に設定する
チェックリストマスタ（定期測定 / 目視巡視 / 異常確認）から項目を読込み、測定値入力 → 基準と自動照合してOK/NG判定。臨時点検も同画面から起票可能。点検結果記録後に承認申請。

📝 作業票を作成（是正 / 計画修繕 / 予防保全 / 緊急対応）
設備に物理的に手を入れる作業を管理する書類。作業種別・担当者・期限・KY/LOTO要否・停止時間・発電影響を記録。

7
担当者 🔐 PTW 承認ゲート
🛡 作業前安全ゲート（PTW / KY / LOTO）
作業を安全に開始するための3つの独立したコントロール。
3つの役割（それぞれ独立）：
🗒 PTW（作業許可証）：高所・電気工事・火気・吊上げ・閉所など特定高リスク作業を事前申請・承認。PTW番号（PTW-YYYY-MMDD-NN）自動発番。承認者のサイン必須。
🧠 KY（危険予知）：作業開始直前にチームで危険箇所・対策を共有するミーティング。ky_records に記録。
🔐 LOTO（施錠・タグアウト）：電気・油圧などエネルギー機器の意図しない起動を物理的に防ぐ。施錠 → 作業 → 解除の3段階をloto_records に記録。

🗄 DB設計の考え方
承認ステータス設計
inspection_plans
inspection_results
defect_findings
work_orders
└ 全て approval_status 列を持つ

work_permits のみpermit_status
（許可証の性質上、ワークフローが異なるため）
DBロック設計
承認済みレコードへの UPDATE は
DBトリガーでブロック
（記録の改ざん防止）

差戻し後の再編集は
approval_status = 'returned' → draft
に戻してから編集可能
テーブル間の紐づき
inspection_plans（PN-番号）
└ inspection_results（plan_id）
  └ result_checklist（result_id）
  └ defect_findings（inspection_result_id）
    └ work_orders（defect_finding_id）
      └ work_permits（work_order_id）
      └ ky_records / loto_records
安全設計上の注意点
• RLS は現在無効
　（フロントは anon キーのみ使用）
• service_role キーはフロントに置かない
• データ推測 UPDATE 禁止
　（候補ビュー → 人が確認 → 確定行のみ）
• バックフィル時のみ
　DISABLE TRIGGER が必要
💡 DB設計は現状概ね正しい ですが、今後の拡張として：
① work_permits の permit_status を approval_status に統合する選択肢（一貫性向上）
② staff_qualifications テーブルと inspection_plans.responsible_person を FK で結ぶ（資格期限確認）
③ SCADA データ（scada_30min）と inspection_results を turbine_id + executed_date で結んで自動参照値を入れる、といった強化が考えられます。
