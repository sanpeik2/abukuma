これは設計メモです（現時点では未実装）。 いまは構築中・実データ未投入のため現状の構成のままでOK。本番運用前に「② Supabase側で AI読取専用View ＋ 専用キー」を実装するための整理です。

0大前提：「学習されない」と「安全」は別問題

商用APIは明示的にオプトインしない限り入出力を学習に使わない、と各社が説明しています（OpenAI API / Anthropic API とも）。ただしそれは 学習リスク の話であって、漏洩・誤操作リスク はまた別です。

学習されない≠何でも渡してよい

「学習しない設定」でも残るリスク：

#残るリスク中身
①送信そのものその時点で機密データを外部サービスに渡している
②APIキー漏洩キーが漏れれば第三者が同じAPIを叩ける
③service_role 漏洩DBを広範囲に読まれる・書かれる・消される
④ログ残留プロンプト/ログに故障詳細が残る可能性
⑤社内規程・契約「外部AI投入禁止」に該当する場合がある

結論：APIで学習しない設定ならかなり安心。でも会社機密をそのまま渡すのは別リスク。だから「渡す範囲」を絞る。

1本当に危ない構成（これは避ける）

# 一番危険なパターン
Claude Code / AI ツール
   ↓  service_role key（フルアクセス・RLSなし）
本番DB を直接読む
   ↓
故障詳細・契約金額・個人情報まで全部見える／消せる

Supabaseが悪いのでも、Claude Codeが悪いのでもありません。「どのキーを渡し、どのテーブルを読ませているか」が問題です。

2安全な3層構成

① 本番DB（フルデータ）
故障詳細・契約金額・修理見積・個人情報・点検票原本。AIからは直接触らせない。
▼ 集計・匿名化
② 朝会用View（絞った安全データ）
停止台数・重大アラーム件数・点検予定・可用率・匿名化した故障カテゴリだけ。ai_morning_briefing_view
▼ 読取専用キー
③ AI用キー（読取専用・View限定）
朝会用Viewだけ読める anon + RLS。書込・削除は不可。service_role は渡さない。

3AIに渡してよい／渡さない

渡してよい（朝会に必要な範囲）
  • 本日停止：3基
  • 重大アラーム件数：2件
  • 本日の点検予定：5件
  • 期限超過の有無
  • 前日比 可用率：-1.8%
  • 要注意カテゴリ：ピッチ系・油圧系（匿名化）
渡さない方がよい
  • メーカー名
  • 契約金額・修理見積
  • 詳細な故障原因（生データ）
  • 作業員名・個人情報
  • ベンダー報告内容
  • 保険・保証交渉の内容

4最低限これだけ守ればかなり安全

✓
service_role key をAIツールにもローカルにも渡さないフロントは anon（publishable）キーのみ。これは公開前提で安全。
✓
.env をGitHubに絶対上げない.gitignore に登録。キーは環境変数 / Supabase Secrets に。
✓
AIが読む専用View（朝会用）を1つ作るまずは ai_morning_briefing_view 一本でよい。

面倒なのは最初の一回だけ。この仕切りを作れば、安心してAIを毎朝使える。

5実装イメージ（後で②で着手）

朝会用View（集計・匿名化）

create view ai_morning_briefing_view as
select
  count(*) filter (where status='standby')   as 停止台数,
  (select count(*) from alarm_events
     where severity='critical' and resolved_at is null) as 重大アラーム件数,
  (select count(*) from inspection_plan
     where planned_date=current_date)             as 本日点検予定,
  ... -- 可用率・故障カテゴリ（匿名化）など
from turbines;
-- ※ 個別の故障詳細・契約・個人名はSELECTに含めない

AI用ロール（読取専用）

-- View だけ select 可。本番テーブルへの直接権限は与えない
grant select on ai_morning_briefing_view to ai_readonly;
-- RLS / GRANT は要件確定後にまとめて適用（今は触らない）

※ 現在DBは28テーブルともRLS無効・「今は触らず進める」方針。RLS / 権限設計は本番運用前にまとめて実施する想定。

6進め方（フェーズ）

いま
構築中・実データなし → 現構成のままでOK。Claude Codeで画面・SQL・ビューを自由に作る。便利さは維持。
本番前
① ai_morning_briefing_view を作成 → ② AI読取専用キー/ロールを分離 → ③ service_role をAIから外す → ④ 故障/契約/個人情報はViewのSELECTから除外。

「開発中はClaude Codeで便利に作る → OK」「本番運用はAIに見せる範囲だけ絞る → 必要」。全部ダメではなく、出口だけ絞る。
