異常発見 → 是正 「考え方」フロー図

阿武隈風力発電所 O&M OS / 点検で異常を見つけた後、頭の中でどう判断するか（Issue #13 詳細版）
大原則：見つけても、すぐ交換しない。
「故障を見つけた＝交換」ではない。まず 5つの軸で一次評価 し、A〜Fのどれに進むか を決める。 記録だけでよいのか／簡易補修か／部品交換か／原因調査(RCA)か／変更管理(MOC)か／即停止かを、感覚ではなくルールで分岐させるのが本フローの目的。

STEP 1〜3 ｜ 発見してから判断するまで

STEP 1 ｜ INPUT
① 点検・巡視・SCADAで「おかしい」に気づく
油漏れ／異音／異常振動／温度上昇／ボルト緩み／腐食／センサー値異常／ブレード損傷／電気盤の焦げ跡 など。
inspection_resultsalarm_events(SCADA)
↓「異常あり」を選ぶと…
STEP 2 ｜ 起票
② 異常・故障候補として独立起票する
点検実績の中に埋もれさせない。「誰が・いつ・どの風車で・何を」を記録し、追跡できる1件にする。
defect_findingsattachments(写真→BOX)
↓※異常なしでも「正常の根拠」を残す（下記）
重要：「異常なし」は判定であって根拠ではない。 「問題なかった」ではなく 「何の基準に対し、実測いくつだから正常」 という適合の積極的証明を残す。 これが無いと、後で同じ箇所が壊れたとき「なぜ見逃したか」を説明できない。

点検「正常」の根拠 例（実測値 × 判定基準）

ギア油温実測 65℃ ／ 基準 上限80・警報75 → 範囲内
主軸受振動実測 2.1 mm/s ／ ISO 10816-21 ゾーンA(<2.8) → 良好
潤滑油分析鉄粉 8ppm・水分120ppm ／ 基準 <15・<300 → 範囲内
ボルト締結マーキングずれなし ／ 規定 580±30 N·m
ブレーキ残厚実測 8.2mm ／ 交換限界 5mm → 余裕
絶縁抵抗実測 120MΩ ／ 規定 >1MΩ → クリア
端子盤サーモ最高42℃・ΔT3℃ ／ 偏熱なし(ΔT<10)
ブレード目視クラック・エロージョンなし＋写真・前回比 変化なし
×「異常なし」 → ○「油漏れ・異音・変色なし（目視＋打音）」と定性も明記

アラーム「問題なし」の根拠 例（消した理由）

自動クリアコードXXX、継続8秒で自動復帰・停止せず
正常帯へ復帰油温ピーク78℃→3分で68℃(基準内)
一過性過去14日 再発0回
気象相関高温アラート＝外気35℃と整合／強風時yaw頻発＝設計想定内
関連値整合温度上昇だが負荷・油圧・回転数は正常＝機器異常でない
メーカー許容OEM許容トリップ回数/日 の範囲内
記録先 alarm_events.disposition / disposition_reason
DBで根拠を強制： result_checklist に measured_value / unit / criteria_min / criteria_max / criteria_text / judgment_basis / prev_value を追加。 ビュー v_checklist_evidence が in_range（基準内か）・delta_from_prev（トレンド）・ evidence_gap = OK判定なのに根拠が空 を自動判定し、監査ギャップを炙り出す。

STEP 3.5 ｜ 5軸を点数化してリスクを定量化する

感覚で「ヤバい」を判断せず、発電プラント標準の リスクマトリクス（影響度×発生可能性）＋FMEAの検出性補正 で数値化する。 参考：ISO/IEC 31010（リスクマトリクス）、IEC 60812（FMEA/RPN）、API 580/581（RBI）、SAE JA1011（RCM）。

運転影響なし1制限3停止5
保安規定影響なし1要確認3あり5

スコアは「どれだけ急ぐか」を決める。「どの作業か(A〜F)」は下の判定で決める。
Supabaseで自動算出済み：ビュー v_risk_score が risk_assessments＋defect_findings から risk_score / risk_band / suggested_urgency / suggested_action(A〜F) / rca_escalation_flag を計算する。 Budibaseはこのビューを表示するだけ。検証例：停止×多発×原因不明 → R=25・F停止／出力制限×再発 → R=9・C交換／原因不明×影響中 → R=3でもD(RCA)へ。

STEP 4 ｜ スコア＋性質で「どの道に進むか」を判定（A〜F）

判定は上から下に向かって重くなる。赤（高/停止/不明/多発/保安規定あり）が1つでも出たら、Aには行かずD〜Fを疑う。

A記録のみ（軽微）

この道に進む条件
  • 安全影響＝低
  • 運転影響＝なし
  • 原因＝明確
  • 再発なし・保安規定影響なし
やること
  • 点検実績に記録＋写真添付
  • 次回点検で再確認
  • 必要なら監視項目に追加

  • 原因が明確

C部品交換

  • 劣化・寿命・破損が確認できる
  • 交換で再発可能性が低い／MOC不要
やること

  • Permit / KY
  • 交換→試運転→復旧確認→クローズ

DRCA（根本原因調査）

条件（1つでも該当）
  • 原因が分からない
  • 同じ故障が再発／多機で発生
  • 重大事故・大きな停止損失の恐れ
  • メーカー想定外／交換しても再発しそう
やること
  • まず暫定措置 → RCA起票
  • 事実整理→仮説→根本原因特定
  • 恒久是正案→（必要ならMOC）→効果確認
rca_investigationscorrective_actions

EMOC（変更管理）

条件
  • 設備設定・保護値を変える
  • 点検周期・作業手順(SOP)を変える
  • 部品型式・運転条件を変える
  • 安全/品質/保安規定に影響する変更
やること
  • MOC申請→変更前後の記録
  • リスク評価→承認
  • Permit/KY→実施→有効性確認→クローズ
moc_changesapprovals

F安全・保安規定（即対応）

条件
  • 人身災害の恐れ
  • 火災・感電・落下・倒壊の恐れ
  • 保安規定の停止条件に該当しうる
  • 法令報告・主任技術者判断が要りそう
やること
  • 即時停止 or 制限運転
  • 現場安全確保→責任者へエスカレーション
  • 保安規定確認→作業許可→証跡→承認クローズ
work_orders(priority=urgent)approvals

補足 ｜ 「是正」には3つの種類がある（混ぜない）

① 暫定是正
目的：安全確保・被害拡大防止（その場しのぎでOK）
停止／隔離／仮固定／監視強化／出力制限／立入制限
② 恒久是正
目的：根本的に再発を防ぐ
部品交換／設定変更／手順変更／点検周期変更／教育／設計変更
③ 予防処置（横展開）
目的：同型機・類似設備へ展開
他WTGの一斉点検／同一ロット確認／メーカー照会／予備品追加／点検項目追加

STEP 5〜7 ｜ どの道(B〜F)も最後はここに合流する

A以外（B・C・D・E・F）はすべて、下の共通レールに乗ってクローズまで進む
↓
④ 作業計画 → 安全統制（PTW / LOTO / KY）
いつ・誰が・どんなリスクで作業するかを固め、現場に出る前と直前で安全を二重・三重に縛る。この3つは別物で、役割も順番も違う。
PTW / LOTO / KY の関係
PTW（作業許可証）が「親」。その許可の中で、LOTO（機械を止めて施錠）と KY（危険予知）が 着手の前提条件として動く。LOTOとKYの両方が済んで初めてPTWが有効化され、作業に着手できる。
① 計画段階
PTW 申請
作業内容・リスクレベルを記入。LOTO要否／隔離要否／作業中止風速を設定。
→
② 承認
PTW 発行
監督者が承認＝issued。これが無いと現場に入れない。
→
③ 当日・着手直前
LOTO ＋ KY
エネルギー源を隔離・施錠・タグ（LOTO）し、チームで危険予知（KY）。両方OKでPTWを active に。
→
④ 作業〜完了
解除 → クローズ
作業完了→LOTO解除→PTWを closed。証跡をBOXへ。
●PTW ＝ 作業許可証
「この作業をやってよい」という許可の枠（親）
誰が・いつ・どんなリスクで作業するかを定義し、承認者が発行。LOTO要否・隔離要否・作業中止風速もここで決まる。状態は draft→issued→active→closed。
work_permitspermit_statusrisk_level
●LOTO ＝ 施錠・タグ付け
機械を「絶対に動かない」状態にする物理的手当て
電気・油圧・回転体などのエネルギー源を止め、ロックして札を掛ける。PTWの安全条件であり、危険作業では必須。loto_required＝true の作業は実施・確認が前提。
work_permits.loto_requiredisolations_required
●KY ＝ 危険予知
着手直前に現場チームで行う「頭の安全確認」
今日の作業に潜む危険項目を洗い出し、行動目標を決めて唱和・確認。特定のPTWに紐づく（permit_id）。風速・天候もここで最終確認。
ky_records.permit_id → work_permits.idhazard_items
↓LOTO＋KY完了 → PTW有効化 → 着手

この流れの中で AI がやること（判断は代行しない）

AIは 決めない・消さない。あくまで人の判断を速くする支援役。
・過去の類似故障を検索 ・RCA要否の参考コメント ・原因仮説の整理 ・是正案のたたき台 ・再発防止策の提案 ・クローズレビューの要約
