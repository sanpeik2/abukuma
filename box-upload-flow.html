証拠写真アップロード設計

点検実績への写真添付 / 案B：Edge Function はアップロードURL発行のみ・写真は BOX 直アップロード
📝 設計メモ（未実装・実装可否は後日判断）
設計思想： 証拠写真の正本（システム・オブ・レコード）は BOX に置く。Supabase には写真そのものを保存せず、 box_file_id または BOX URL などの参照だけを持つ。これによりストレージの二重管理・費用を避け、 文書ガバナンス（保存期間・権限・監査）は BOX 側に一元化する。

1なぜ「Edge Function は URL 発行だけ」なのか

案A：ブラウザ → Edge Function → BOX（中継）不採用

Function が写真バイナリを受けて BOX に転送。

  • 実装はシンプル
  • ❗ Edge Function にはリクエストボディ上限・実行時間制限がある
  • ❗ 高解像度・複数枚で詰まりやすい（タイムアウト/サイズ超過）

案B：Function は発行のみ・写真は直アップロード採用

Function は BOX のアップロード先URLを発行するだけ。写真はブラウザから BOX へ直接送る。

  • 大容量・複数枚でも安定（Function を経由しない）
  • BOX の認証情報（秘密鍵）はサーバー側だけに留まる
  • Function は軽量・短時間で完了

2処理シーケンス

1
ブラウザアップロード要求
点検実績フォームで写真を選択 → Edge Function に { result_id, filename, size } を送信（Supabaseの認証トークン付き）。
2
Edge FunctionBOX アップロードURLを発行
サービスアカウントの鍵（Supabase Secrets に格納・フロントに出さない）で BOX API を呼び、 対象フォルダ宛ての直アップロード用URL（一時）を取得してブラウザに返す。
※ BOX のチャンク/プリフライト系APIを利用。フォルダは「号機／年月」等で自動振り分け。
3
ブラウザ → BOX写真を直接アップロード
受け取ったURLへ写真本体を PUT/POST。Supabase / Edge Function を経由しないので大容量でも安定。 完了すると BOX から file_id が返る。
4
ブラウザ → Supabase参照情報を保存
inspection_attachments に box_file_id 等を INSERT。 誰が・いつ添付したかも証跡として記録。写真本体は Supabase に入らない。

4BOX 認証方式（要決定）

サービスアカウント（JWT / CCG）

  • システムが代表して書き込み
  • BOX上のフォルダ・権限を一元管理しやすい
  • 証跡の uploaded_by は Supabase 側ユーザーで担保

ユーザー個人の BOX（OAuth）

  • BOX 上も個人名義で残る
  • 各ユーザーが BOX アカウント必須・トークン管理が複雑
  • フォルダ権限の設計が重くなりがち

→ 運用負荷とフォルダ統制の観点ではサービスアカウントが有力。最終判断は後日。

5セキュリティ要点

  • BOX の秘密鍵・クライアントシークレットは Supabase Secrets（サーバー側） のみ。フロントには絶対に置かない。
  • Edge Function は Supabase の認証トークンを検証し、ログイン済ユーザーだけがURL発行を要求できるようにする。
  • 閲覧時はURL直貼りより、都度 Edge Function で一時リンクを取得する方が漏洩しにくい。
  • inspection_attachments も将来的に RLS で書込権限を制御（点検実施者・主任など）。
