▶ O&M業務から見たデータ構造（業務別ビュー）

「この業務のとき、どのテーブルを見て、どのライブ画面で操作するか」。技術ER図の前に、業務の順番で読む地図。
1
監視
SCADA・KPI・健全度を眺め、異常の予兆を拾う
alarm_events daily_kpi component_risk_dashboard 🌅 朝会コックピット 🌀 風車カルテ
2
異常検知
点検・巡視で異常を見つけ、記録して起票する
inspection_results result_checklist defect_findings 🛠 点検実績入力
3
一次判断 (A〜F)
5軸で評価し、記録だけ／補修／交換／RCA／MOC／即停止を分岐
defect_findings.initial_judgement risk_assessments 🔧 故障/RCA 🧭 考え方フロー
4
作業票
直す作業を指示書（WO）にする
work_orders ★ 📝 作業票一覧
5
安全・法令確認
作業許可(PTW)・LOTO・KYで安全に止めてから着手
work_permits ky_records 🔒 作業許可(PTW)
6
作業実施
作業を行い、結果・部品交換・所見を記録する
work_orders.status parts_usage maintenance_results
7
復旧確認
直ったか・再発しないかを確認する
closeout_reviews 🔧 故障/RCA
8
クローズ・承認
主任技術者が証跡を確認して承認・クローズ
approvals attachments(BOX) ✅ 承認待ち一覧
9
再発防止・横展開
真因を断ち、他号機へ展開。設定変更はMOCで管理
rca_investigations corrective_actions moc_changes near_miss_reports ⑦ RCAの基本

▼ ここから下は技術ER図（開発・設計者向け）

テーブルの主キー・外部キー・参照関係の詳細。上の業務別ビューで「どのテーブルか」を掴んでから読むと分かりやすい。
マスター 点検 異常・是正フロー 作業 在庫 安全・変更 承認・証跡 人事・契約 AI

▶ 点検→故障発見→是正→クローズ フロー（Issue #13）

inspection_plans→ inspection_results→ defect_findings→ risk_assessments→ rca_investigations / moc_changes→ corrective_actions→ work_orders→ work_permits→ ky_records→ closeout_reviews→ approvals / attachments(BOX)

マスター

turbines
PK id
風車台帳（46基）。多くのテーブルが turbine_id で参照
om_users
PK id = auth.users.id
担当者。assigned_to / created_by / owner 等で参照
inspection_rules
PK id
点検ルール。計画・チェック項目が参照
fault_codes
PK id
故障コード。チェック項目・作業票が参照
parts
PK id
部品台帳。在庫・使用履歴が参照

点検

inspection_plans
→ rule_id rules / turbine_id turbines / assigned_to users
inspection_results
→ plan_id plans / turbine_id turbines。has_anomaly で異常起票へ分岐
result_checklist
→ result_id results / rule_id rules / fault_code_id fault_codes

異常・是正フロー

defect_findings
→ turbine_id / source_id（点検/SCADA/巡視/NM）。一次判定 initial_judgement
risk_assessments
ポリモーフィック → target_type/target_id。recommended_action で A〜F分岐
rca_investigations
→ work_order_id / defect_finding_id。根本原因調査
corrective_actions
→ work_order_id / rca_id / defect_finding_id
closeout_reviews
→ work_order_id。復旧確認・横展開・クローズ

作業

work_orders ★中心
→ turbine_id / result_id / defect_finding_id / fault_code_id。番号 WO-自動採番
work_permits
→ turbine_id / work_order_id。番号 PTW-自動採番。LOTO/隔離/風速制限
ky_records
→ turbine_id / work_order_id / permit_id。hazard_items(jsonb)

在庫

parts_stock
→ part_id parts。現在庫・最終入庫
parts_usage
→ work_order_id / part_id。使用履歴

安全・変更

near_miss_reports
→ turbine_id。事故知識DB・AI傾向分析対象
moc_changes
→ turbine_id。設定/保護値/周期/手順変更の監査証跡

承認・証跡

approvals
ポリモーフィック → target_type/target_id。承認/却下履歴
attachments
ポリモーフィック → target_type/target_id。BOX証跡リンクのみ保持

人事・契約

staff_qualifications
→ staff_id staff_roster。資格失効 expires_at 管理
vendor_contracts
契約台帳。end_date・auto_renewal・予告日数

AI（DELETE禁止）

ai_usage_logs
provider(openai/anthropic/gemini)・token・cost 記録
ai_decisions
→ linked_work_order_id / permit / near_miss / moc。人間が approved_by_human で承認
凡例: ★=異常管理の中心テーブル / 「ポリモーフィック」=target_type+target_id で複数テーブルを参照。
本図は本番Supabaseスキーマ（information_schema）を正本とする。詳細列定義は Supabaseテーブル定義書.md を参照。
